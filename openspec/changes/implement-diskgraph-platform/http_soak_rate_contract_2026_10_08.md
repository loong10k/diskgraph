# 持续HTTP验收的速率契约

沿用RE-04/07，保留实际包60秒持续查询、原HTTP外层300秒以及20k/200k整个工作流300秒门禁。此前持续夹具不限速发送请求，而实际MCP CLI使用`HttpLimits::default()`，每客户端所有连接共享50次/秒令牌桶。稳定性负载需要明确提供速率，不能通过提高服务限额、忽略429或不断重试消除失败。

本增量以每秒最多40次发起查询，给原控制请求保留余量；按实际开始时间间隔，不在慢请求后补发积压。等待和网络调用继续使用原单调截止时间，不延长总时长。报告增加`offered_max_requests_per_second`，并保留实际请求数、实际耗时及最后4096次延迟。该阶段是声明速率的持续稳定性烟测，不是吞吐上限或并发压力资格证明；既有独立超限拒绝测试及并发负载仍需通过。

验收场景：

- 快速成功响应也不能忙循环、突发补发或延长原期限。
- 429、权限错误、错误scope、空结果、预算错误和网络异常仍立即失败，无重试。
- 慢响应按实际调用时间推进，单次等待不得超过原剩余期限；5000次采样仍限制为4096条。
- 失败仅输出允许列表业务分类、HTTP状态和布尔字段，不输出主体、路径或正文。
- 当前CI `37771002316`的Linux ARM/x86与Windows包原持续步骤失败记录保留；旧脚本隐藏了错误分类，不能声称原生返回429已经证实。候选必须在后续同SHA原生包验收通过后才关闭该失败。

本地红灯已复现：新增快速响应测试在旧不限速实现达到时钟观测保护而失败。实现后13项持续夹具测试通过；脚本全量318项，317通过，1个Windows原生Job测试本机跳过。真实服务持续运行及平台包仍待验证，不关闭整体生产任务。

实际socket的`over_rate_requests_are_refused_with_429`回归通过；归档组成11/11通过。本机重新构建实际CLI/MCP成功，但完整HTTP脚本在隔离索引阶段返回`unsupported`（exit 6），尚未进入持续请求；没有把这次失败当作通过，也没有安装或绕过宿主保护。

同轮macOS ARM包原持续阶段另外出现原生`TimeoutError`。现有日志未记录剩余期限，不能断言是末段请求期限过短或服务停顿。本增量补充原异常的安全数值note（已完成请求数、开始时剩余毫秒、请求耗时、总耗时、提供速率），保持异常对象、失败和期限不变。缺少note时测试真实失败，补充后通过。原生失败仍待后续候选实际验证。
