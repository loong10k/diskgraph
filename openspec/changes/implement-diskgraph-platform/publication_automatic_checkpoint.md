# 发布提交与自动 WAL 维护边界

Windows 200k 扩展诊断显示正式发布 SQL/聚合/封印约 3.6 秒，而随后 commit 约 96.5 秒。默认 SQLite 自动 checkpoint 可能在 commit 内执行；这是待回归确认的原因，不能把扩展诊断当作原 300 秒验收通过。

验收：checked 扫描发布保留 WAL/NORMAL 及原末检、原子回执和控制 fence，提交期间不得因自动 checkpoint 把 WAL 复制到主库。使用真实隔离磁盘数据库、阈值 1 的正向对照验证；不能仅检查是否执行显式 PRAGMA。成功、拒绝、回调 panic 后均恢复原连接自动 checkpoint 配置。可信兼容入口及 Engine 已提交结果路径仍执行显式维护；维护失败不改写已提交事实。不得移除容量门禁、忽略 WAL 增长或从全流程性能计时中扣除维护。

Windows 原生 Rust 1.99 已确认行为 RED：阈值 1 的 checked 发布在显式维护前就将 revision 写入主库；回执恢复后真实 WAL 仍有 708672 字节。修复后发布回归 7/7、恢复回归 8/8；Store 全部行为测试 397 通过，来源注释修正后布局测试 1/1，通过合计 398，12 项既有忽略。文档测试、两包格式及全部目标 Clippy 通过。日志摘要、原失败与源码指纹见 `docs/benchmarks/windows_publication_checkpoint_2026_10_09.json`。

当前状态：上述定向行为与存储检查完成，当前提交完整 Engine、同 SHA 三平台 CI 及 200k/300 秒验收仍待验证，整体生产门禁保持未完成。配置恢复失败会记录诊断，不能将已提交事实伪装为未提交；没有据此声明原生文件操作可用或严格 RSS/墙钟上限。
