# Windows Git 超时隔离诊断

沿用 PF-06 / D29 的原15秒整次采样、输入/输出额度、外部恢复责任及默认并发全量验收。此文记录定位实验，不修改生产要求，不把诊断通过视作生产资格。

## 2026-10-09 当前提交的反例

使用台式机 `d3fae86b` 对应原生 Engine 测试二进制（22599680字节，SHA-256 `0a498e88a61f54745c7cb96ce95355c82dc159f27b0cd6e00c9c7f9c21e4bf6f`），同时启动8个独立测试进程，各自使用隔离仓库、真实产品采样及原15秒预算。8项全部在首次 unborn 采样失败，总21.391秒。随后单进程同样失败，总40.735秒，但已经通过首次 unborn 采样，在 committed 采样失败。不能将前述默认全量82项失败全部解释成测试并发过高；单进程也有可观察反例。本实验不覆盖全量、跨平台、真实远程服务或生产负载。

目录打开诊断复用产品的访问/共享/no-reparse/no-recall标志，以保留父句柄的相对 NtCreateFile 遍历临时目录及仓库路径；120+80次原生打开未出现共享冲突，最大1.613ms。第二次同样200次未见冲突，但调度并未证明与8进程采样实际重叠。只检查目录类型，没有完整产品卷/身份检查，不能当作目录能力资格，也不能据此排除间歇共享冲突。未放宽 share-read 或身份检查。

新增显式忽略的原生出生时点诊断：只在真实 CreateProcess 后记录有界64个时点，在采样返回后输出；分别观察 unborn / committed，保持原15秒预算、原采样路径及测试宿主恢复责任。真实采样失败仍应报告失败。恢复时间单列，不能算作预算内完成；默认全量不运行该诊断，更不能通过忽略既有失败来获得绿灯。下一步用实际出生序列判断时间耗在出生前准备、命令执行还是末段输入/清理。

首轮实际诊断1/1通过：unborn 14次真实出生、8.491秒，committed 13次、7.703秒，恢复增量均不足1ms。前述单进程和8进程失败保留，没有以本次通过覆盖。出生间隔约0.5秒，下一步以相同清空环境及同一 `git --version` 对照普通宿主调用与原受管理探针，区分Git/系统启动成本和探针自身成本；不先假设批处理一定有效。

## 同环境启动对照及恢复反例

增加普通 `Command::output` 与真实受管理探针的四轮 `git --version` 对照，均清空环境，仅保留 PATH/SystemRoot，不改变产品选用的可执行程序。普通调用为 633298、541293、640582、569341 微秒，受管理调用为 746692、687161、687902、669574 微秒；四轮均成功。此数据表明普通 Git 启动已有显著成本，不能把全部延迟归因于受管理探针。

同一次诊断随后失败：unborn 实际启动14个子进程，采样15.003891秒；committed启动9个，采样15.004290秒。两者仍使用原15秒期限。原测试宿主实际退休后的总时间分别15.195348秒及31.975355秒；后者存在约16.97秒额外恢复时间，是仍待处理的反例，不能算预算内完成。此轮测试明确为失败1/1，未用上一轮通过结果覆盖。

安装布局只读对照同样保留失败风险：cmd/git.exe 的第一轮普通版本调用21.531秒，其余三轮0.531至0.735秒；mingw64/bin/git.exe 四轮0.406至0.469秒，libexec/git-core/git.exe 四轮0.390至0.437秒。该实验没有改变产品工具路径，没有证明显式受信程序可被内部二进制替换，也没有确立安全软件或其他应用的因果关系。Python同步超时不是硬实时保证，单条21.531秒观察保留。

最终诊断源码在Windows Rust1.99.0/MSVC运行 `cargo clippy --locked -p diskgraph-engine --lib --tests --target x86_64-pc-windows-msvc -- -Dwarnings` 成功；不是全量资格。最终test文件SHA-256为 `db4727dce4b5ae03c8d74d3cc95979cd5e3da95f08a279b7cabb681f1ec0901e`，mod文件为 `f6aaf75edb2203d30a277c29933db3a183c2eb6f78b8880bb300edc85fa171ec`。首轮出生诊断发生在增加版本对照前，不能以最终源码指纹绑定首轮通过。
